# 项目架构与实现说明

## 1. 项目定位

本项目是一个“简历分析 + 模拟面试 + 知识库问答 + 管理后台”的一体化系统，面向求职者和管理员两类角色。

- 用户侧目标：
  - 上传简历
  - 获取 AI 简历分析结果
  - 基于简历发起模拟面试
  - 查看历史分析与面试记录
  - 使用知识库问答能力
- 管理侧目标：
  - 管理用户账号
  - 配置 AI 接口
  - 配置模拟面试跳转地址
  - 管理管理员密码
  - 管理用户启用/停用、删除、重置密码

---

## 2. 技术路线

本项目采用“前后端分离 + 容器化部署 + 异步任务处理 + 可配置 AI 接口”的技术路线。

### 2.1 前端

- 技术栈：
  - `React`
  - `TypeScript`
  - `Vite`
  - `Tailwind CSS`
  - `Framer Motion`
  - `React Router`
- 设计特点：
  - 用户端与管理员端共用一套前端代码仓库
  - 通过构建参数 `VITE_ADMIN_PORTAL` 生成两套独立前端产物
  - 用户端和管理员端分别由不同 Nginx 容器承载

### 2.2 后端

- 技术栈：
  - `Spring Boot`
  - `Spring Data JPA`
  - `PostgreSQL`
  - `Redis`
  - `Spring Mail`
  - `Spring AI / OpenAI Compatible API`
- 设计特点：
  - 业务模块分层清晰
  - 核心耗时任务采用异步处理
  - AI 服务地址、Key、模型名支持后台动态配置

### 2.3 基础设施

- `PostgreSQL`：保存业务数据
- `Redis`：缓存会话、限流、异步队列/流
- `MinIO`：对象存储，保存简历和知识库原文件
- `Docker Compose`：统一编排
- `Nginx / 宝塔反向代理`：对外访问入口
- `Cloudflare`：域名与 HTTPS 外层加速/防护

## 3. 总体架构

可以把系统理解成 5 层：

### 3.1 表现层

- 用户前端
- 管理员前端

### 3.2 API 层

- Spring Boot REST API
- 负责鉴权、校验、业务编排、状态返回

### 3.3 业务层

核心模块：

- `auth`：登录、注册、邮箱验证码、找回密码、Turnstile 校验
- `resume`：简历上传、解析、分析、历史记录
- `interview`：面试题生成、会话管理、答题、评估
- `knowledgebase`：知识库上传、向量化、问答
- `admin`：后台配置、用户管理、AI 设置

### 3.4 数据与异步层

- PostgreSQL：结构化数据
- Redis：
  - 会话缓存
  - 限流
  - Redis Stream 异步任务

### 3.5 存储与外部服务层

- MinIO：原始文件存储
- 外部 AI 模型服务：
  - 默认兼容 OpenAI 风格接口
  - 可切换到不同厂商
- SMTP 邮件服务：
  - 当前接入 Resend SMTP

## 5. 后端模块设计

后端代码主模块位于：

- `app/src/main/java/interview/guide/modules`

### 5.1 `auth` 模块

职责：

- 用户登录
- 用户注册
- 邮箱验证码发送
- 邮箱找回密码
- Turnstile 人机校验
- 管理员账号初始化

当前认证方案：

- 使用账号密码登录
- 管理员与普通用户共用登录接口，但由前端路由和角色控制进入不同入口
- 管理员默认账号通过环境变量初始化

本次定稿后的找回密码逻辑：

- 不再使用密保问题
- 统一改为邮箱验证码

注册逻辑：

- 用户注册时必须填写邮箱
- 必须先发送验证码并验证成功
- 开启 Turnstile 防刷

### 5.2 `resume` 模块

职责：

- 简历上传
- 文件解析
- 去重
- 元数据保存
- 调度 AI 分析
- 历史查询
- 重新分析

处理流程：

1. 校验文件大小、类型
2. 解析文本
3. 上传原文件到 MinIO
4. 保存简历记录到数据库
5. 将分析任务投递到 Redis Stream
6. 异步消费者执行 AI 分析
7. 前端轮询简历详情页展示结果

对应核心服务：

- `ResumeUploadService`
- `ResumeParseService`
- `ResumePersistenceService`
- `ResumeGradingService`
- `ResumeHistoryService`

### 5.3 `interview` 模块

职责：

- 根据简历生成面试问题
- 创建面试会话
- 暂存答题状态
- 提交答案
- 生成评估报告

处理流程：

1. 用户基于简历创建会话
2. AI 生成问题列表
3. 会话和当前进度写入 Redis
4. 答题过程增量保存
5. 面试完成后投递评估任务到 Redis Stream
6. 异步消费者生成评估结果
7. 前端轮询查看最终报告

对应核心服务：

- `InterviewSessionService`
- `InterviewQuestionService`
- `AnswerEvaluationService`
- `InterviewPersistenceService`
- `InterviewHistoryService`

### 5.4 `knowledgebase` 模块

职责：

- 知识库文件上传
- 文本解析
- 向量化
- 问答检索
- RAG 会话管理

处理流程：

1. 上传文件
2. 文件去重
3. 保存原文件到 MinIO
4. 保存知识库记录到数据库
5. 将向量化任务投递到 Redis Stream
6. 异步消费者完成切片和向量写入
7. 查询时使用向量检索和 RAG 生成结果

对应核心服务：

- `KnowledgeBaseUploadService`
- `KnowledgeBaseParseService`
- `KnowledgeBaseVectorService`
- `KnowledgeBaseQueryService`
- `RagChatSessionService`

### 5.5 `admin` 模块

职责：

- 管理员权限校验
- 用户管理
- AI 配置管理
- 模拟面试地址管理

当前后台配置的意义：

- 管理员不必改服务器 `.env`
- 可以在页面直接更换 AI 提供商
- 可以直接切换模拟面试外部链接

核心服务：

- `AdminGuardService`
- `AdminUserService`
- `AdminResumeAiSettingsService`

## 6. AI 接口实现方式

### 6.1 统一采用 OpenAI Compatible Route

本项目不是只绑定某一家模型厂商，而是走“OpenAI 兼容接口”思路。

也就是说，只要供应商支持类似下面这种接口风格，就能接入：

- Base URL
- Bearer API Key
- `/v1/chat/completions`

### 6.2 后台可配置项

管理员可在后台修改：

- API 地址
- API Key
- 模型名称
- 模拟面试地址

这意味着：

- 可以从阿里百炼切换到别的兼容厂商
- 可以替换模型名
- 不需要改前端源码

### 6.3 简历分析实现方式

简历分析不直接把模型响应原样展示，而是要求模型严格输出 JSON。

系统做法：

- 预置系统提示词 + 用户提示词模板
- 请求模型时指定 `response_format=json_object`
- 后端将 JSON 解析为结构化对象：
  - 总分
  - 分项得分
  - 优势
  - 改进建议

这样做的好处：

- 输出稳定
- 前端容易渲染
- 便于导出与存档

### 6.4 面试生成与面试评估

面试也是结构化 AI 流程：

- 先生成问题
- 再基于用户回答生成评估结果

因此整个系统本质上是两个 AI 处理链：

- 简历分析链
- 面试评估链

另有一个：

- 知识库 RAG 问答链

## 7. 异步任务设计

这是项目的一个关键架构点。

### 7.1 为什么要异步

AI 分析、面试评估、知识库向量化都属于耗时任务。

如果同步处理，会导致：

- 上传接口阻塞
- 页面等待时间过长
- 用户体验差
- 容易请求超时

### 7.2 当前实现

项目使用：

- `Redis Stream` 做任务投递
- 后端消费者处理异步任务

典型任务：

- 简历分析任务
- 面试评估任务
- 知识库向量化任务

### 7.3 前端如何配合

前端拿到初始结果后，不等待 AI 直接返回最终内容，而是根据状态轮询：

- `PENDING`
- `PROCESSING`
- `COMPLETED`
- `FAILED`

这套机制已经在多个页面统一实现。

### 10.1 用户登录页

用户登录页采用独立风格页面，支持：

- 登录
- 注册
- 邮箱验证码
- 找回密码
- 中英文切换

### 10.2 管理员登录页

管理员登录页与用户端分离：

- 不提供注册
- 只保留管理员登录入口
- 风格与用户页不同

### 10.3 邮箱方案

当前使用：

- SMTP Host：Resend SMTP
- 发件用途：
  - 注册验证码
  - 找回密码验证码

注意：

- 域名发信验证是在 Resend 完成的
- 系统本身只负责 SMTP 调用，不负责域名发信认证

### 10.4 Turnstile 方案

当前使用 Cloudflare 官方脚本接入，不做自建镜像。

原因：

- 维护成本更低
- 安全性更高
- 兼容官方参数与校验逻辑

## 11. 生产部署架构

### 11.1 容器结构

生产环境通过 `docker-compose.prod.yml` 启动以下容器：

- `postgres`
- `redis`
- `minio`
- `createbuckets`
- `app`
- `frontend`
- `frontend-admin`

### 11.2 对外访问方式

当前线上采用：

- 用户站点：`https://mianbaojob.xyz`
- 管理入口：当前仍通过独立前端容器访问

实际链路是：

1. 浏览器请求域名
2. Cloudflare 接收 HTTPS
3. 宝塔/Nginx 反向代理到本机容器
4. 前端容器再将 `/api` 代理给后端 `app`

### 11.3 用户端和管理端为什么分两个前端容器

因为两边虽然共用一套代码仓库，但入口和路由意图不同。

拆开部署的好处：

- 用户端和后台端互不污染
- 后台入口更独立
- 前端静态资源组织更清晰

### 11.4 HTTPS 方案

当前线上已完成：

- 域名接入
- HTTPS 可访问
- 反向代理可用

## 13. 如果技术人员问你“为什么这样设计”

你可以用下面这套话回答：

### 13.1 为什么用前后端分离

因为前端交互较重、后台管理独立、后续部署也更灵活。

### 13.2 为什么用异步任务

因为 AI 分析和向量化都比较慢，同步会严重影响体验，所以采用 Redis Stream 异步化处理，再由前端轮询状态。

### 13.3 为什么 AI 接口做成可配置

因为模型供应商可能会切换，后台可配置可以减少后期改代码和重发版的成本。

### 13.4 为什么对象存储和数据库分开

因为原文件适合放对象存储，数据库只保存元数据和业务结果，这样更稳、更容易扩展。

### 13.5 为什么用户端和管理端分开部署

因为两者角色、入口、交互目的不同，拆开后更清晰，也更方便后续做独立域名和权限隔离。
